01 · Orientation

What this project actually is

Second agent in the Agent OS suite, after the ROI Agent, and built on the same split that made that one defensible.

AxcelAI sells automotive semiconductors through distributors into Tier-1s and OEMs. A socket is won over years: you promote a part, ship samples, the customer evaluates, designs it in, and eventually you get a design win that turns into mass production — or you lose it. David Nam tracks that in TrackF (1).xlsx: six tabs, 28 live rows, and one hand-entered Confidence Level per opportunity that multiplies every revenue figure in the file.

This agent replaces the workbook as the system of record. It ingests the pipeline, recomputes every currency figure deterministically, calibrates the confidence number against context, moves records between lifecycle states, and keeps an audit trail behind numbers that end up in a board pack.

The one design decision everything else follows from

Four fields touch money: V1 EAU, V3 Distributor ASP, J1 Confidence and T1 quarterly units. Two formulas turn them into every dollar in the system. The model is allowed to propose a change to J1 and to nothing else — so no inference call can alter a figure a reviewer sees.

02 · The source workbook

How to use TrackF.xlsx

It has three jobs, and only one of them survives into the product. Knowing which is which is most of the intake design.

The workbook plays three roles, and it is worth being explicit about all three:

  1. Specification. Its columns are the field list. Every parameter in the registry traces to a column letter on a named tab, which is what makes the schema reviewable by David rather than invented by us.
  2. Regression oracle. Its own formulas are the test fixture. test_calc_engine.py already asserts our Python reproduces ProjectTrack exactly for all 9 live rows. Every calculation added in §05 gets the same treatment before it ships.
  3. First month of data. A one-time backfill, hashed and stored as an immutable snapshot. It is not the runtime store — from Phase 2 the database is.

04 · The progress model

Nine tracks. Each one is a question a sales manager actually asks, the signal that answers it, and the field it has to come from.

The workbook records progress as a single overwritten cell: Design Status changes and the old value is gone. That is the one thing to stop doing. Invariants the calc layer must hold

  • Purity. Layers 1–4 are pure functions: same snapshot in, same numbers out, no I/O, no network, no clock. That is what makes a past figure reproducible in an audit.
  • Blocking findings exclude the row from totals. A skeleton row with no ASP contributes zero today and looks like a real zero. It should be excluded and counted, not silently added.
  • Units are declared, not assumed. EAU is Kpcs so V1 × V3 lands in $K without a conversion. Every ParamSpec carries its unit so that stays checkable rather than remembered.
  • Recompute rather than store. When an approved confidence lands, C2 is recomputed deterministically from the new J1 — no second model call, no cached figure that can drift from its inputs.
06 · Judging layer

The judging matrix

Two matrices and a set of bounds. The first says what a valid opportunity looks like and what confidence it starts at; the second says what may move it, by how much, and on what evidence.

Matrix A — valid pairings and baseline confidence

David's answer was that confidence follows the stage, and that qualitative analysis on top is welcome. That only works if the baseline is written down: without it the agent invents a number instead of justifying a deviation from an agreed one, which is far harder for a reviewer to check. The values below are our proposal, derived from what the workbook actually does, and they are the one thing we need ratified before the judgment layer can be finished.

✕ marks a pairing David's rules forbid: Design Win only at PVT or MP, Design In from DVT to PVT, Sample and Evaluation and Promotion at Concept or EVT. One open item — the Stage column holds only Concept, EVT, DVT and PVT today, while the answer uses MP as a stage. Confirm MP is a Stage value.

Why a 0.95 ceiling changes the arithmetic

apply_confidence_adjustment clamps to [0, 1], and both design wins in the sample sit at exactly 1.00. Any positive support the agent gives a locked win is therefore discarded, so the calibrated total can only ever move down. Ratifying a ceiling below 1.00 gives the design_win_lock_in rule somewhere to put its points, and makes the whole layer two-directional instead of a one-way haircut.

  • R2.1 — Opportunity ID on every row of every tab. The structural blocker under everything else. Five severed joins close with one field. Format and backfill owner still unassigned.

  • R2.4 — Canonical enums. Region, Design Status, Stage, Product Line, Application, loss reason. Held in reference tables, versioned.
  • R2.5 — Provenance per field value. Source, timestamp and trust on every value, so a nightly CRM sync cannot silently revert a correction a manager made that morning.
  • R2.6 — Competitor Part# on the tab that carries confidence. One column copy restores a rubric rule.
  • R2.7 — Unit/Set captured at intake. It exists in the workbook and was dropped from the POC's sample data, so the set-volume calculation has nothing to run on.
  • R2.8 — Retained vintages. When EAU or confidence changes, keep the previous value. Forecast accuracy is the highest-value output this agent could produce and it cannot be measured without them.
  • R2.9 — NRE as its own record type. Not a design status, not a volume row.

R3 · Judgment

  • R3.1 — The model may write exactly one field. Enforced by the service returning confidence only, not by a runtime check.
  • R3.2 — Bounded movement: per-factor caps, a per-run cap, and a [0.05, 0.95] clamp.
  • R3.3 — Every factor cites a rule ID and a verbatim quote. No citation, no proposal.
  • R3.4 — Reply shape fixed by JSON schema on the request, never by asking for JSON in the prompt.
  • R3.5 — Rubric and baselines are versioned config a person edits, not learned weights, and the version in force is stored on every event.
  • R3.6 — Retrieval filters before it searches: same region and product line, same part or socket where known, resolved within eight quarters, top-k 6, hard token budget.
  • R3.7 — Numbers are never embedded. A figure recovered from a vector search is a figure nobody can audit.
  • R3.8 — Customer pricing is never embedded, because retrieval crosses region boundaries by design.

Connector precedence

The moment more than one source can write a field, you need provenance on every value and a rule for who wins. Precedence runs human entry > ERP shipped > distributor POS > CRM declared > external inferred. A lower-precedence source that disagrees with a higher one does not lose quietly — it raises a reconciliation item through the same gate as a confidence proposal. That is how a stale CRM stage, or an EAU that contradicts the platform build forecast, surfaces as a question instead of a silent overwrite.

Of the whole connector list, the distributor POS/POR feed is worth more than the rest combined: it is already a standard report in most distribution agreements, and it is exactly the actuals that both blocked analyses in §05 are waiting on.
