Opportunity Tracking Agent/ Product surface/UI, chat, integrations, API

What people actually touch

Ten screens built around direct entry rather than a spreadsheet drop, rendered four different ways for the four people who use them; an assistant that is allowed to explain but never to decide; a role model enforced in the query rather than the interface; and the three machine surfaces — MCP, REST and webhooks — that let the rest of the platform consume a weighted forecast without anyone re-keying anything.

The landing view answers one question before anything else: what is the weighted pipeline, and what moved it since the last run? Every figure here is calc-engine output at a named snapshot — the run banner says which one, because a forecast without a vintage is not a forecast.

03 Screen

Adding an opportunity

The workbook is one intake path, not the intake path. Direct entry in the UI is the primary route and the only one that captures owner, evidence and a reason for the confidence figure at the moment a person actually knows them. Import exists for migration and for regions not yet on a CRM — and everything it writes is marked lowest trust.

01Direct entry

A person fills the form below. Owner, region and evidence are captured at source, and Matrix A is shown live so a deviation is a conscious act.

02CRM sync

Salesforce creates the row on opportunity creation; the owner completes the commercial fields in-app. No re-keying.

03Bulk import

Workbook or CSV, column-mapped with a preview and a dry-run validation pass before anything commits. For migration and backfill.

04API / MCP

POST /v1/opportunities for another system to create rows under a scoped service account.

A reviewer can approve, override with their own value, or reject — and all three write an audit event.

07 Screen

Ask OppTrack — the assistant

The chat panel is a reader of the system, not a second path into it. It answers from the same tables the dashboard renders, quotes the same audit events a reviewer would open, and has no tool that writes a confidence value. When it reports a figure it says which snapshot and which engine produced it, so an answer in chat and an answer in a board pack cannot disagree.

09 Screen

Integrations

Every connector writes provenanced field values, never raw cells. Connector precedence

When two sources supply the same parameter, the winner is decided by this order, not by whichever ran last. A lower-trust source that disagrees with a higher one raises a conflict instead of losing silently, so a wrong ERP price is visible rather than absorbed.

RankSourceWins forOn disagreement
1Human edit, in-appAny field, including confidenceAlways wins; connector raises a conflict and holds
2ERPPrices, part numbers, datesOverwrites CRM, flags if the delta exceeds a threshold
3CRMOwnership, customer, stageOverwrites upload, never overwrites ERP price fields
4Distributor POSActuals onlyNever writes a forecast field; feeds accuracy analysis
5Workbook uploadAnything not yet connectedLowest trust; every value it sets is marked fallback
—The agentJ1 proposals onlyWrites to the queue, never to the record

Service accounts are scoped to exactly one connector and cannot write confidence, move a record, or act as a person. That is why a compromised integration key cannot change a forecast — the worst it can do is supply a wrong input that the validation rules then flag.

11 Screen

Three cells carry the whole separation of duties: an owner cannot approve their own number, a manager cannot edit the rubric that judges it, and an admin who can edit the rubric cannot ratify what it produces.

Nobody, at any level, can edit an audit entry. Deleting a person's account anonymises their display name and leaves their decisions in place, because removing the actor would break the chain.

How it is enforced

1  Identity     SSO assertion  →  role + region scope, from the directory. Never self-set.
2  Query        every SELECT is wrapped: WHERE region = ANY(:scope). Not a UI filter.
3  Route        FastAPI dependency asserts the role before the handler runs.
4  Field        confidence is rejected on PATCH /opportunities for every role, always.
5  Decision     proposal.owner_id != actor.id is checked in code, not in the interface.
6  Audit        actor, role and scope are written with every mutation, before it returns.

The test that matters: call the API directly with a manager token for another
region and you get 404, not a filtered list. A 403 would confirm the row exists.

Every export carries the snapshot ID and the rubric version in its header or filename. A forecast that circulates without a vintage is the failure this whole system exists to remove, and an export is exactly where that discipline gets lost.

14 Documentation

What ships alongside the product

Six documentation surfaces, each with one audience. The split matters because the person ratifying Matrix A and the person integrating the MCP server have almost nothing in common except that both will be blocked without a doc written for them.

DocAudienceAnswersLives
Getting startedRegional sales ownerHow do I enter an opportunity and what happens to itIn-app, first-run tour
Reviewer handbookSales managerWhat each factor means, when to override, what approving commits you toIn-app, linked from every proposal
Matrix A and the rubricDirector, financeBaseline per pairing, factor caps, why a number movedVersioned page, published by admin
API and MCP referencePlatform engineersEndpoints, tool schemas, auth, idempotency, webhooksOpenAPI 3.1 + MCP manifest, generated
Connector guideIT, integratorsField mapping, trust levels, precedence, conflict resolutionRepo docs, per-connector page
Architecture and auditEngineering, complianceThe layers, the guards, retention, how to reproduce a runRepo docs, this set

Generated, not written by hand

OpenAPI 3.1      from the FastAPI route signatures      → /v1/openapi.json
MCP manifest     from the same tool definitions          → /mcp/manifest.json
Rubric page      from registry/rubric.py + Matrix A      → versioned, diffable
Parameter dict   from registry/parameters.py ParamSpec    → one table, 28 live entries
Validation rules from validate/rules.py REQUIRES          → what fires, and what it needs

The rule: if a doc can drift from the code, generate it. The rubric page in particular
must be generated, because a reviewer trusting a stale factor cap is worse than
having no page at all.

The reviewer handbook is the one document that decides whether this product works.

Everything upstream is engineering discipline; the value only lands if a sales manager reading a proposal at 8am understands what J-05 is claiming and feels able to reject it.
