Following the same approach we used for the ROI Agent, I have worked through the architecture for the second agent Gene asked for, the Opportunity Tracking Agent (tracks the sales pipeline from early evaluation through design win to mass production or loss, using David's TrackF_1.xlsx as the template). Here is where things stand.
The core design decision, same as the ROI Agent: the pipeline math stays deterministic code, the LLM only calibrates one input. TrackF_1.xlsx's ProjectTrack tab computes Sales Revenue as EAU (in thousands of units) times Distributor ASP, then Adjusted Revenue as Sales Revenue times a human-entered Confidence Level, essentially an expected-value weighted pipeline. I reimplemented this in Python (calc_engine.py) and it reproduces the sheet's own numbers exactly for all 9 sample projects, verified with a regression test (test_calc_engine.py). The LLM's job, in judgment.py, is to calibrate that Confidence Level against context: is the Design Status (Design Win, Design In, Sample, Evaluation, Promotion) consistent with the validation Stage (Concept, EVT, DVT, PVT), is a competitor part named against the same socket, does a locked-in Design Win at DVT or PVT deserve support rather than a discount. It returns a structured, cited adjustment, never a raw revenue number.

Running it: python3 run_poc.py runs end to end with zero setup, using a rule-based MOCK judgment layer (clearly labeled in the output) so you can see the whole pipeline shape before touching any API key. It prints the portfolio's weighted pipeline revenue before and after calibration, with the specific factors that moved each project. To go live: pip install anthropic, set ANTHROPIC_API_KEY, rerun, same code path, real reasoning instead of the mock rules.

Two data issues to fix before building further on this template, not blockers for the POC but real before production: the FCST_Revenue tab's regional roll up rows for Europe, Taiwan, and Japan currently throw #REF! errors (broken cell references), and Sheet1's "Projection" versus "Stretch" quarterly numbers do not tie back to any other tab by formula, so their exact definition needs to come from David or Gene directly rather than being reverse-engineered from the file. Both are called out in the attached Step 1 document.

What is next, roughly in priority order: replace the hand-written JSON input with a real intake form covering the Funnel and ProjectTrack fields (region, customer, part number, stage, EAU, ASP, confidence). Stand up Postgres for pipeline records and stage history, treating stage history as an append-only log per project rather than just a current-state field, since win rate and time-in-stage analysis both need that history preserved. Wrap calc_engine.py and judgment.py as two callable services, compute_pipeline_rollup and score_confidence, so the Workflow Manager can call each independently. Build a stage tracking service that watches for projects stalled unusually long in one stage and flags the moment a project resolves to Mass Production or Design Lost, though whether that move should happen automatically or wait for human confirmation is still an open question for David. Require a reason code on Design Lost entries (price, technical fit, relationship, timing) so a win and loss model has something to learn from later. And build the hand-off to the ROI Agent: once a project hits Design Win, its Adjusted Revenue by year is exactly the shape of input the ROI Agent's revenue forecast intake expects, so that contract should be designed once, shared, rather than reinvented on either side.

On hardware: no new purchase needed. This agent's workload is lighter than the ROI Agent's judgment calls, so the same RTX PRO 6000 Blackwell card (96GB) we sized for that agent covers this one too, served through the same shared vLLM deployment rather than a second one. Route through a hosted frontier API as the primary path for the same reasons as the ROI Agent (cost at this volume, and avoiding the Chinese-model security concern entirely), keeping the Blackwell card as the fallback. If we ever do self-host, Western open-weight models only, Llama, Mistral, Gemma, or Command R+, never Qwen or DeepSeek.

Hi all,

Three things: what I found looking into Salesforce, where David's answers left the open questions, and the architecture I've written based on both. A short list at the end details what we need before building starts.

Salesforce

Salesforce already does our arithmetic, and its AI can't help us yet.

Its Opportunity object carries Amount, Stage, Probability and Expected Revenue, where Probability follows Stage, and Expected Revenue is Amount times Probability. That's exactly TrackF's Sales Revenue times Confidence Level, and David told us confidence follows the stage a project sits in. So the stage-to-confidence table we keep asking him for is, in Salesforce terms, just the probability attached to each stage in the picklist. Worth knowing we're not inventing something odd. It also has Forecast Category, which separates how far along a deal is from how confident anyone feels, and that's the Design Status versus Stage tension we keep hitting. Manufacturing Cloud is built for our business model and keeps the design-win pipeline in a separate forecast set from the committed forecast, mirroring the split David made when he handed the forecast to finance.

Where it stops helping: Einstein Opportunity Scoring needs 200 closed-won and 200 closed-lost opportunities from the last two years before it will train on your data. We have nine live projects and one lost record (In the sheet we got for now). Below that bar, it falls back to a generic model built on other companies' data, and its known weakness is that you can't tell it which fields matter. Our judgment layer requires no history because it reasons from a written rubric and must cite a source for every adjustment.

Open questions

Of the thirteen we put to David, six are properly answered, and seven have a direction, but not enough to build from. Fifteen more have never been asked. Four to send him this week:

What confidence number goes with each stage? He said confidence follows the stage, but never gave the table, and Concept, EVT, DVT, PVT and MP each need a figure. Without them, the agent invents a number instead of justifying a deviation from an agreed-upon one.
If a design win isn't 1.00, what's the ceiling, and how much does dual sourcing and cancellation risk take off?
Does anything stop a person, or does the agent close and promote records on its own?
Is there a corrected workbook? He wrote, "I don't see it in the sheet I updated", and ours still has the broken roll-up rows.

Reading the workbook cell by cell also turned up five things nobody has asked about, including a whole revenue type for NRE and licences that has no volume and no confidence, and Funnel and FCST_Revenue disagreeing by a factor of ten on EAU for the same part. All five are written up in the tab and field map.

Architecture

Step 5 doc attached, six diagrams. It covers what Step 2 named but didn't specify: how someone gets an account, what the tables look like, what the agent remembers between runs, and how evidence reaches the model.

Four decisions worth arguing about. No public sign-up, with region scope enforced in the SQL rather than by hiding things in the UI, because this pipeline holds unannounced design wins and customer pricing. Memory is six tiers, and only one is a vector store, since most of what the agent needs to recall is exact and relational. state_history is the piece that earns its keep first, because it turns Design Status from a cell that gets overwritten into an event stream, which gives us stall detection, time in stage, win rate and the outcome labels calibration will need. Retrieval filters by region and recency before it searches. Numbers are never embedded, since a figure recovered from a vector search is one nobody can audit.

Phase 0 needs none of it. No database, no auth, no model. Run it against today's workbook, and it already finds a company total that won't compute, seven TBD values in numeric fields, five skeleton rows carrying design wins worth zero, and a Funnel row implying a third of global light-vehicle production.
