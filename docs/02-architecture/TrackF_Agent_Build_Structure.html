FIG. A LAYER STRUCTURE

Seven layers, one registry running through all of them

The structural decision that makes everything else fall out: a parameter registry is the single source of truth, and every layer declares which parameter IDs it needs rather than assuming they exist. Add a parameter and the modules that declared a dependency on it activate on their own — no hunting through code for what to switch on.

FIG. B RUN PIPELINE

What happens on one ingest

A run is a pure function of a snapshot. It never mutates the source, never writes confidence directly, and always terminates in a queue a person has to act on. Re-running the same snapshot reproduces the same numbers and the same proposals.

Nine tables, all hanging off one ID

This is the parameter dictionary rendered as schema. Everything the workbook keeps in parallel tabs becomes rows related to a single opportunity — which is what turns the five severed joins into real foreign keys.

CONTRACTS THE THREE THAT MATTER

Interfaces worth fixing before you write features

Everything else can be refactored freely. These three shapes are what keep the layers honest, so pin them first.

1 · ParamSpec — the registry entry

Every parameter from the dictionary becomes one of these. Validators, analyses and judge rules all reference parameters by ID, never by column name.

@dataclass(frozen=True)
class ParamSpec:
    id:          str            # "V1", "J1", "L2"
    name:        str            # "EAU"
    dtype:       type
    unit:        str | None     # "Kpcs", "USD", None
    enum:        tuple | None    # canonical values, if any
    required:    bool
    source_tabs: tuple[str, ...]
    present:     bool           # False for P0/P1 not yet collected

2 · Analysis — declares what it needs

This is what makes the LIVE / PARTIAL / BLOCKED status in the catalogue computed rather than hand-maintained. Add a parameter to the registry and the blocked analyses light up by themselves.

class Analysis(Protocol):
    id:       str
    requires: tuple[str, ...]        # param IDs, e.g. ("T1","T2","P1-2")

    def run(self, ctx: RunContext) -> AnalysisResult: ...

# the registry, not the analysis, decides whether it may run
def runnable(a: Analysis, reg: Registry) -> bool:
    return all(reg[p].present for p in a.requires)

3 · ConfidenceProposal — the model's only output

The single shape the LLM is allowed to return. Anything that doesn't parse into this is rejected and retried, then falls back to no-change. Note the bounds: the model cannot drive confidence to a certainty in either direction — only a human can.

@dataclass(frozen=True)
class ConfidenceProposal:
    opportunity_id: str
    prior_j1:       float
    proposed_j1:    float
    factors:        list[Factor]     # rule id + delta_pp + evidence quote
    rationale:      str

    def __post_init__(self):
        delta = abs(self.proposed_j1 - self.prior_j1)
        assert delta <= MAX_DELTA_PP / 100      # bounded movement
        assert 0.05 <= self.proposed_j1 <= 0.95  # never 0.0 or 1.0
        assert self.factors                     # no unexplained change
FIG. D DATA ACQUISITION

What can be fetched, and what never can

Roughly two-thirds of the parameter dictionary can be populated without anyone typing. The remaining third is the part that carries the commercial judgment — and automating it would destroy the thing the tracker exists to record. The split is clean enough to design around.

FIG. E CONNECTOR LAYER

Fetched data must never silently overwrite a person

The moment more than one source can write a field, you need provenance on every value and a rule for who wins. Without it, a nightly CRM sync quietly reverts a correction a regional manager made that morning — and nobody can tell it happened.

On automating lead generation specifically

The direct version — scraping the world for new design-win opportunities — has poor economics in automotive semi. Sockets are won through RFQs and multi-year relationships, and by the time a programme is public the design-in window has usually closed. The high-yield inversion is white-space detection: licence the vehicle programme database, list every platform with an SoP inside your design-in horizon, match it against your product lines by application, and flag the ones where you have no registered opportunity at all.

That produces a short, specific, checkable list — "Hyundai/Kia has four platforms with 2028–29 SoP in lighting and we are registered on one" — rather than a feed of press releases. It uses the same programme data you would buy for EAU validation, so the marginal cost is near zero once Tier 2 exists.

SEQUENCE BUILD PHASES

What to build, in what order

Phases 0 and 1 change nothing about how your sales teams work — they read the workbook as it is today. Only from Phase 2 does the intake change.

SIX PHASES — EACH ONE SHIPPABLE ON ITS OWN
PhaseBuildDeliversNeeds from the business
0 · Read-only registry · intake · normalise · validate A data-quality report against the existing workbook. Finds the #REF! totals, the TBD numerics, the Funnel/FCST date contradictions. Nothing. Runs on today's file.
1 · Numbers calc · rollup · 7 live analyses Reproduces every workbook figure, plus attach rate, channel margin, concentration and coverage that the sheet never computed. Ratify the L1 → J1 baseline rubric.
2 · Identity Postgres · opportunity · state_history · crm_connector Stable IDs, real joins across tabs, stage-entry dates, stall detection. If a CRM exists, most of this arrives by sync rather than by typing. Add ID, owner and last-updated to intake. One-time backfill. CRM read access.
3 · Judgment judge · queue · audit · review UI Cited confidence proposals with a human gate and a permanent audit log — the two things your terms doc already mandates. Reviewer role assigned. Loss reason codes required at close.
4 · Learning snapshots · disty_pos · erp_connector · accuracy · calibration Forecast bias per region and per owner; confidence calibrated against what actually shipped. The actuals arrive by feed, not by hand. Distributor POS/POR report scheduled. ERP extract. Two quarters before it says anything useful.
5 · Outside-in market_data · EAU cross-check · white-space Validates EAU against real platform build forecasts, enriches competitor detail, and lists programmes in your horizon with no opportunity registered against them. A vehicle programme data licence. This is the only phase with a recurring external cost.

Phase 0 is worth shipping alone. It needs no schema change, no database and no model — and on the current file it already finds a company total that doesn't compute, four TBD values sitting in numeric fields, and an SoP date that disagrees between two tabs. That is a credible first demo built entirely from Layers 0–2.
